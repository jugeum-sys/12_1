# 과제 12 - 퀵 정렬의 피벗 선택에 따른 성능 비교

`gcc -O2 -o quick_compare quick_compare.c` 로 컴파일한다. 실행하면 난수 시드를 묻고, Enter를 누르면 기본 시드(12345)로 아래 결과가 재현된다.

비교 횟수는 **분할 과정에서 데이터 값과 피벗 값을 맞대어 본 횟수**를 센다. Median-3이 중앙값을 고르기 위해 쓰는 비교(2~3회)도 포함했다. 세 방법은 피벗을 고르는 부분만 다르고 분할 알고리즘은 완전히 같으며, 크기마다 같은 원본의 복사본을 사용했다. 모든 경우 오름차순 정렬이 확인되었다.

## 1. 크기별 비교 횟수 (단일 실행)

| n | First | Random | Median-3 | n log₂n |
|---|---|---|---|---|
| 1,000 | 10,237 | 10,291 | 10,882 | 9,000 |
| 2,000 | 24,148 | 27,274 | 24,746 | 20,000 |
| 4,000 | 54,612 | 52,435 | 50,872 | 44,000 |
| 8,000 | 111,939 | 128,616 | 112,499 | 96,000 |
| 16,000 | 277,885 | 267,083 | 258,918 | 208,000 |
| 20,000 | 332,511 | 341,082 | 324,455 | 280,000 |

한 번만 재면 세 방법의 차이가 **잡음에 묻힌다.** n=1,000에서는 Median-3이 오히려 가장 많이 나왔다. 피벗을 어떻게 고르든 무작위 데이터에서는 평균적으로 비슷한 분할이 나오고, 그날 데이터가 어떻게 섞였느냐가 수 % 차이를 만들기 때문이다. 그래서 크기마다 새 데이터로 **30회 반복한 평균**을 따로 측정했다.

## 2. 크기별 30회 평균

| n | First | Random | Median-3 | First/Med3 | Random/Med3 |
|---|---|---|---|---|---|
| 1,000 | 11,000 | 10,987 | 10,759 | 1.022 | 1.021 |
| 2,000 | 24,927 | 24,934 | 24,012 | 1.038 | 1.038 |
| 4,000 | 54,885 | 55,014 | 52,713 | 1.041 | 1.044 |
| 8,000 | 121,853 | 120,671 | 115,008 | 1.060 | 1.049 |
| 16,000 | 266,310 | 264,501 | 250,645 | 1.062 | 1.055 |
| 20,000 | 341,017 | 337,616 | 319,197 | 1.068 | 1.058 |

**세 방법 모두 n이 2배가 될 때 비교 횟수는 약 2.2배씩 늘었다.** n²이라면 4배, n log n이라면 약 2.2배여야 하므로 세 방법 다 O(n log n)으로 동작하고 있다. 실제 값도 n log₂n의 1.2배 안팎으로 이론값(2n ln n ≈ 1.39 n log₂n에서 하위 항을 뺀 값)과 맞는다.

**Median-3이 모든 크기에서 가장 적었고, n이 커질수록 이득이 커졌다.** 1,000개에서 2% 차이가 20,000개에서 6.8%까지 벌어졌다. First와 Random은 사실상 같았다(차이 1% 미만). 무작위로 섞인 데이터에서는 "첫 번째 원소"도 결국 무작위 값이므로 둘이 같은 셈이기 때문이다.

## 3. 추가 실험: 이미 정렬된 데이터 (2,000개)

| 방법 | 비교 횟수 |
|---|---|
| First | **1,977,153** |
| Random | 27,054 |
| Median-3 | 21,081 |

**피벗 선택이 왜 중요한지는 여기서 드러난다.** 첫 원소 피벗은 정렬된 입력에서 **94배** 더 많은 비교를 했다. 정렬된 배열에서 첫 원소는 항상 그 구간의 최솟값이므로, 분할하면 한쪽은 비어 있고 다른 쪽에 나머지 n-1개가 전부 몰린다. 구간이 1개씩만 줄어드니 재귀 깊이가 n이 되고 비교 횟수는 n²/2 = 2,000,000에 수렴한다. 실제 측정값 1,977,153이 정확히 그 값이다. 즉 **최악의 경우 O(n²)**로 떨어져 삽입 정렬과 다를 바 없어진다.

(이 실험만 n을 2,000으로 줄인 이유는, 첫 원소 피벗이 정렬된 입력에서 재귀 깊이 n까지 내려가 20,000개로 하면 스택이 넘칠 수 있기 때문이다.)

## 4. 피벗 선택이 성능을 좌우하는 이유

퀵 정렬의 비용은 **분할이 얼마나 반반에 가까운가**로 결정된다. 매번 절반씩 나뉘면 구간 길이가 n → n/2 → n/4로 줄어 log₂n 단계 만에 끝나고, 각 단계에서 전체 n개를 한 번씩 보므로 n log n이 된다. 반대로 한쪽이 비는 분할이 반복되면 단계 수가 n이 되어 n²이 된다.

- First는 데이터가 무작위면 무작위 피벗과 다를 바 없지만, 정렬되었거나 역순인 입력에서는 매번 최솟값(또는 최댓값)을 고르게 되어 최악의 경우에 빠진다. 실제 데이터는 이미 정렬되어 있는 경우가 흔해서 이것이 큰 약점이다.
- Random은 어떤 입력이 와도 특정 패턴에 당하지 않는다. 입력이 정렬되어 있어도 27,054회로 정상 동작했다. 다만 평균적으로는 여전히 운에 맡기는 분할이라 Median-3보다 조금 못하다.
- Median-3은 세 값을 보고 그중 가운데 값을 고르므로 **극단적으로 작거나 큰 값이 피벗이 될 확률 자체를 줄인다.** 피벗 하나를 고르는 데 비교 2~3회를 더 쓰지만, 분할이 고르게 되어 전체 비교가 줄기 때문에 그 비용을 충분히 회수한다. 정렬된 입력에서는 첫·가운데·마지막의 중앙값이 곧 구간의 중앙값이므로 완벽한 반반 분할이 되어 오히려 가장 유리해진다(21,081회로 셋 중 최저).

결론적으로 Median-3이 가장 효과적이었다. 무작위 데이터에서 6.8% 적었고, 정렬된 데이터에서는 First 대비 94배 적었다. 즉 평균 성능도 조금 낫고, 최악의 경우를 피한다는 점에서 훨씬 안전하다.

## 5. [보너스] 재귀 퀵 정렬과 반복 퀵 정렬

데이터 10,000개, Median-of-Three, 500회 반복 평균(배열 복사 시간은 따로 재서 뺌)

| | 실행시간 |
|---|---|
| Recursive Quick Sort | 0.597 ms |
| Iterative Quick Sort | 0.609 ms |

비교 횟수는 두 방법이 **완전히 동일**했다(148,385회). 같은 피벗 선택과 같은 분할을 쓰므로 당연한 결과이고, 반복 구현이 올바른지 확인하는 근거이기도 하다.

실행시간은 **거의 차이가 없었다.** 여러 번 돌려 보면 0.60~0.66 ms 사이를 오가며 순서가 뒤바뀌기도 해서, 이 정도 차이는 측정 잡음 수준이다.

차이가 작은 이유는 두 방법이 하는 일이 본질적으로 같기 때문이다. 재귀 호출은 **함수 호출 스택에** 구간 정보(left, right)를 쌓는 것이고, 반복 구현은 **직접 만든 배열 스택에** 같은 정보를 쌓는 것이다. 저장하는 내용이 같으니 작업량도 같다. 재귀 쪽은 함수 호출마다 복귀 주소와 레지스터를 저장하는 비용이 있고, 반복 쪽은 직접 스택을 관리하는 코드가 추가되므로 서로 상쇄된다. 게다가 요즘 컴파일러는 `-O2`에서 꼬리 재귀 등을 최적화해 호출 비용을 더 줄인다.

반복 구현의 진짜 장점은 속도가 아니라 **스택 깊이를 직접 통제할 수 있다**는 점이다. 이 구현은 분할된 두 구간 중 **큰 쪽을 먼저 쌓고 작은 쪽을 나중에 쌓아** 작은 구간부터 처리하게 했다. 이렇게 하면 스택에 쌓이는 구간 수가 log₂n을 넘지 않아, 최악의 입력에서도 스택이 넘치지 않는다. 재귀 구현은 3번 실험처럼 깊이가 n까지 내려가면 프로그램이 강제 종료될 수 있다.
